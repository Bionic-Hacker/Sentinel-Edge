# v0.5.0 — Phase 8: Application security scanning

Everything here runs locally and in CI; no AWS resources exist yet ([ADR-0016](../adr/0016-local-first-phase-order.md)).
Findings are **LOCAL**: real scanner output against this repository, its images and the running
local stack.

## What's new
- **One scan pipeline, locally and in CI:** `make scan` and the `security-scans` CI job run
  Semgrep (registry rulesets plus SentinelEdge's own rules), Bandit, Trivy (lock files and both
  images), Gitleaks, Checkov and Syft. Every scanner runs in an image pinned by digest, as your
  user, with the repository read-only and no Docker socket. ([ADR-0020](../adr/0020-application-security-scan-gate.md))
- **SentinelEdge Semgrep rules:** the project's own rules as code, each with annotated tests:
  SQL never built from strings, outbound HTTP only through the egress guard, verified JWTs, no
  shell commands, no secrets in logs; in the SPA, network calls only through the API client, no
  web storage, raw HTML, dynamic code, inline styles or navigation to computed URLs.
- **The scan gate:** a fixable critical or high finding blocks the build unless an unexpired,
  justified risk acceptance covers it. A package vulnerability with no fix published is reported
  on every run and blocks as soon as a fix appears. The gate fails closed: a scanner that crashed
  cannot let the build pass.
- **Authenticated DAST:** `make dast` runs the ZAP baseline and ZAP's active API scan of every
  endpoint in the OpenAPI document, signed in as a read-only scanner account whose session exists
  only while the scan runs.
- **Vulnerability management:** `make scan-import` stores each scan. Findings are de-duplicated
  across scans, marked fixed only by a scan that no longer reports them, reopened if they return,
  and given a remediation deadline (critical 7 days, high 30, medium 90, low 180). Leads mark false
  positives and accept risks with a justification, compensating control and expiry; an expired
  acceptance reopens its finding. ([ADR-0021](../adr/0021-vulnerability-management.md))
- **Vulnerabilities and SBOM pages:** open findings by severity, past-SLA and awaiting-fix
  counts, the last scan and its gate result; filters kept in the URL; finding detail with the
  moves you are allowed; risk acceptance and revocation. The SBOM page lists every component of
  the API image, web image and source, searchable, with a CycloneDX download.
- **Findings in security operations:** new and reopened critical or high findings are security
  events (source *Application security scan*); a fixable critical one opens an incident. The
  dashboard's Vulnerabilities control and the application inventory now show measured values,
  and the API Security Center shows each endpoint's last authenticated DAST scan.
- **Images take OS security fixes at build time**, and the API image moved to Debian 13.
- **Cross-origin isolation:** COEP `require-corp` alongside COOP on the SPA and the API.
- **Runbook:** [vulnerability remediation](../runbooks/vulnerability-remediation.md).
- `make image-digests` reports pinned images whose tag has moved (`UPDATE=1` rewrites them).

## Fixes and improvements
- `make verify-hardening` waits for the API and never passes a check on a missing response.
- A backend test now fails if the SPA's lists of allowed values drift from the backend's.
- Frontend tests: one ordered cleanup hook, so no `act()` warnings on any machine.
- Scanner rule IDs no longer appear among the dashboard's most matched detection rules.

## Evidence
- 765 backend tests (98.4% coverage) against real PostgreSQL, up from 668; 91 frontend tests,
  up from 75.
- First imports on the owner's machine: 174 findings, the gate blocking on one newly fixable
  CVE; 4 fixed automatically after the build-time OS upgrade, gate passed; the authenticated ZAP API scan reached 66 endpoints and passed every
  active rule (SQL injection on five engines, XSS, path traversal, command injection, SSRF to
  cloud metadata, template injection, Log4Shell), raising only low and informational alerts.
- `make smoke`: 56 end-to-end checks, up from 48.
- Every new page checked in headless Chromium at 1440 and 390 px wide.
- Threat model v0.5 with eight new threats (T-VM-01 to T-VM-08); controls C-CICD-06 to C-CICD-11,
  C-VM-01 to C-VM-06, C-API-13 and C-WEB-04 with their evidence.

## Known limitations
- 44 high OS package vulnerabilities in the Debian 13 base have no fix published; they are
  reported on every scan. A minimal base image is planned with Phase 12 hardening.
- CI scan results reach SentinelEdge when someone imports the CI artifact (`make scan-import
  FROM=...`) until a deployed API exists (Phase 11).

## Upgrading from v0.4.0
Your data is kept; `make dev` applies migration 0009. Then scan and import. See
[local-development.md](../local-development.md#upgrading-from-v040-phase-7-to-v050-phase-8).

```
make dev
make scan
make dast
make scan-import
```
