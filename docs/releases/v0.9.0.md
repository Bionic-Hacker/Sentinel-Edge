# v0.9.0 — Phase 4: the AWS workload

SentinelEdge runs in AWS: PostgreSQL on RDS, the API on ECS Fargate behind an internal load
balancer, secrets in Secrets Manager, logs and alarms in CloudWatch, and the audit chain anchored
in S3 Object Lock. All of it is one switch (`workload`) in the dev stack, created for a deploy
window and destroyed after it ([ADR-0026](../adr/0026-aws-workload-deployment.md),
[runbook](../aws-deploy-window.md)).

Phases 4 and 5 were applied together in one deploy window on 12–13 October 2026. The fixes that
window needed ship in **v0.10.0**, which is the version to deploy; this release records Phase 4 as
built.

## What's new
- **One switch.** `workload = true` creates the database, secrets, internal ALB, ECS and alarms;
  `false` removes them. It refuses to switch on without NAT, an issued certificate and both images
  by digest. Between windows only cents a month remain (zone, certificates, ECR, keys, anchors).
- **Database:** RDS PostgreSQL 17 (`db.t4g.micro`) in the isolated subnets, encrypted under the
  platform key, TLS required (`rds.force_ssl`, TLS 1.2 minimum); the app verifies the server's
  certificate and host name against Amazon's CA bundle (`make rds-ca`).
- **Secrets never in plan, state or logs:** RDS holds its master password; the application's four
  secrets are generated by Secrets Manager during apply and written through write-only arguments.
- **Roles on a non-superuser RDS master:** `db/bootstrap-roles.sh` checks instead of clearing what
  it cannot change, and hands over the schema with `SET` but not `INHERIT`.
- **ECS on Fargate (Spot):** task families `api`, `migrate`, `dbadmin`, `anchor` and `admin`, one
  execution role each reading only its own secrets; read-only root filesystem, non-root, no
  capabilities, no ECS Exec. Images by digest only (`make images-push`), one-off tasks with
  `make ecs-task TASK=…`.
- **Internal ALB:** HTTPS only (TLS 1.3, and 1.2 with forward-secret AEAD ciphers), only the
  platform's host name forwarded, invalid headers dropped, desync mitigation strictest.
- **Audit anchors (completes ADR-0005):** every hour the chain head goes to an S3 Object Lock
  bucket (governance, 30 days); `audit-anchor check` catches the deletion of the newest records,
  which a hash chain alone cannot see.
- **Seven workload alarms** to the security-alerts topic.

## Evidence (the Phases 4–5 deploy window, with the v0.10.0 fixes)
- 93 resources created from reviewed plans, and destroyed again with one switch.
- `dbadmin`: roles and schema in place on RDS as its non-superuser master; `migrate` ran every
  migration as `sentinel_migrator`.
- The API served traffic from Fargate Spot, reaching RDS over verified TLS (`/api/v1/ready`).
- `make edge-check` (v0.10.0): the internal ALB resolves only to private addresses and cannot be
  reached from the internet.
- `Anchored seq=14` and `Audit chain matches the anchor`; the hourly schedule anchored on its own.
- No secret value appeared in any plan or state.
- Threat model v0.9.1: T-ORG-01, T-ORG-03, T-DB-04 and T-SEC-02 mitigated; T-ORG-02, T-DB-01,
  T-DB-02 and T-AUD-01 completed. Controls C-LB-01, C-DB-02, C-DB-04, C-AUD-03, C-SEC-04 and
  C-MON-01 implemented. Capabilities `aws.compute` and `aws.observability` are now Real AWS.

## What the window found (fixed in v0.10.0)
- The Free plan's service control policy denies creating S3 buckets in us-east-1, and its accounts
  launch only Free Tier instance types (the NAT instance is now a `t4g.micro`).
- Task definitions and the RDS parameter group were rewritten on every plan until written exactly
  as AWS returns them.
- Health checks address a task by IP; the Host allow-list refused them until the liveness probe was
  exempted (only `GET /api/v1/health`).

## Known limitations
- Single-AZ database and one NAT in dev; Fargate Spot interruptions are replaced by the service.
- TLS ends at the ALB; the hop to the tasks stays inside the private subnets.
- No keyless route from CI into the account: images and Terraform run from the owner's machine.

## Upgrading from v0.8.0
Nothing changes in the local stack. To deploy, follow [aws-deploy-window.md](../aws-deploy-window.md)
with **v0.10.0**.
